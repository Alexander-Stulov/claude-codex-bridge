MCP elicitations can now be approved.

A fix release: the bridge, its six tools and the wire are unchanged except for how
`codex_approve` answers one request kind, and what `codex_poll` shows for it.

## Elicitations were declined whatever you decided

An MCP server codex is using can ask the caller something mid-turn — an
*elicitation*: a permission prompt (the browser plugin asking to open a tab) or a
short form. codex routes it to the bridge as `mcpServer/elicitation/request`, and
`codex_poll` reported it as an approval of kind `elicitation`. But the reply had
been hard-coded since 0.4.0: `codex_approve(request_id, "allow")` returned
`{"sent": {"action": "decline"}}` and codex reported the action blocked by
permission policy. Command, file-change and permission approvals mapped correctly.

`codex_approve` now answers with the caller's decision, in the shape codex's
app-server protocol defines for it — `McpServerElicitationRequestResponse`,
`{action, content?, _meta?}` in the schema `codex app-server generate-json-schema`
emits for codex-cli 0.153.4:

- `allow` sends `{"action": "accept", "content": {}}`. codex reads a bare accept as
  `content: {}` itself; it is sent explicitly so the reply is a complete MCP
  `ElicitResult` however the MCP server checks it.
- `deny` sends `{"action": "decline"}`.
- `allow_always` sends accept with `_meta.persist = "session"`, and `allow_class`
  the durable `"always"`, when the request offers that mode — codex lists the
  modes it will honour in the request's `_meta.persist`, and the bridge never sends
  one that was not offered. When it has to accept once instead, `note` says so.
- A form: `grant` carries the answers, an object keyed by field name (a JSON string
  works too). Required fields are checked before anything is sent, and a refused
  grant leaves the request pending, so it can be retried with the fields filled in.

## Also in this release

- `codex_poll` shows what an elicitation is asking: `server`, `message`, `mode`,
  `requested_schema` (`url` for a URL-mode request), plus `tool` and
  `persist_modes` when codex attached them to one of its own MCP tool-call
  approvals.
- An elicitation for a thread the bridge is not tracking is still declined, now as
  `{"action": "decline"}` rather than a command decision — codex logged the old
  reply as malformed before falling back to declining.
- The tool descriptions and the built-in instructions say that elicitations can be
  approved and what `grant` means for them.
- `tests/smoke.py` covers allow, deny, session and always persistence, a
  schema-bearing form, a URL-mode request and the untracked-thread path.

Install: download `claude-codex-bridge-v0.13.3.mcpb` below. macOS: double-click it.
Windows: Claude Desktop → Settings → Extensions → Advanced settings → Install
Extension, from a local folder — Desktop refuses files on network paths, and Windows
has no `.mcpb` file association. Then restart Claude Desktop. Needs Python 3 on the
machine (`python3` on macOS, `python` on Windows) and codex installed before Desktop
starts. Prerequisites and the full documentation are in the
[README](https://github.com/Alexander-Stulov/claude-codex-bridge#readme).
