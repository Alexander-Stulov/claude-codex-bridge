The bridge runs the newest GPT-6 models, and the 1M-context scripts know them.

OpenAI has released GPT-6.1 Sol, GPT-6 Sol and GPT-6 Luna, and codex 0.159.0 lists
them beside GPT-6 Astra.

## Family names follow the newest model

A family name now runs that family's newest model, so a caller who asks for Sol gets
the current Sol without knowing its version:

| Name | Was | Now |
|---|---|---|
| `luna-medium`, `luna-high` | GPT-5.6 Luna | GPT-6 Luna |
| `terra-medium`, `terra-high` | GPT-5.6 Terra | GPT-6 Luna |
| `sol-high`, `sol-xhigh`, `sol-ultra` | GPT-5.6 Sol | GPT-6 Sol |
| `astra-*` | GPT-6 Astra | GPT-6 Astra |

GPT-6 has no Terra, so `terra-*` runs GPT-6 Luna. The names are unchanged, so callers
that route work by them keep working.

## Pinned names run exactly the model they name

To run one specific model, name it: the model's slug plus the effort. For example,
`gpt-5.6-sol-high`, `gpt-5.6-terra-medium`, `gpt-6.1-sol-xhigh` or `gpt-6-luna-high`.
Pinned names cover GPT-6.1 Sol, GPT-6 Astra, Sol and Luna, and GPT-5.6 Sol, Terra and
Luna. Each offers the same effort levels as its family (no `gpt-6-astra-low`, as there
is no `astra-low`), and it never moves when the family does. The tool description
tells callers to use a pinned name only when the user asks for a specific model.
Otherwise they use the family name.

Some threads ran on a model their family has since left: a thread from before this
release, or another client's thread. `codex_poll` and `codex_fork` now report such a
thread under its pinned name (`gpt-5.6-terra-high`, say) instead of the family name,
so they show the model it really ran on, and a fork stays on that model. A thread on a
family's current model still reads back under the family name, and a `terra-*` thread
reads back as `luna-*`, because both run the same model.

## A named model is never silently swapped

- **Steering keeps the running model.** A submit to a thread whose turn is still
  running steers that turn, and a steer carries input only, so it cannot change the
  model. Until now, a steer that named a different model was accepted and quietly ran
  on the old one. Now it is refused, and the message says to interrupt or wait, then
  submit. Any name for the running model still steers.
- **Resuming reads the model from codex.** A thread the bridge resumes now takes its
  model from codex's own record, even when the caller passes a name. The new name
  applies once the new turn actually starts. If that turn fails to start, the thread
  still reports the model its last turn really ran on.

## The 1M-context scripts raise the new models

- **The new models were hidden.** `model_catalog_json` makes the copied catalog
  codex's whole model list, and codex stops fetching its own while it is set. On a
  copy built before these models existed, neither the Codex app nor the CLI listed
  them.
- **Re-running the old script would have shown them, but capped.** The script raised
  only `gpt-6-astra` and `gpt-5.6-*`, so it would have copied the new models in at
  the stock 272,000 cap (258,400 effective), with no warning.

Both editions now raise `gpt-6.1-sol`, `gpt-6-sol` and `gpt-6-luna` to 1,050,000, next
to `gpt-6-astra` and `gpt-5.6-*`. Both `context_window` and `max_context_window` are
set, so each thread gets 997,500 effective, the same as the other raised models. The
GPT-6 models are listed one by one rather than matched by a `gpt-6` prefix. A cap
above what a model takes upstream is not safe, so a new line (a GPT-6.2, say) is
raised only once the script lists it. Each entry still matches as a prefix, as
`gpt-5.6-` always has, so a variant such as `gpt-6-sol-*` is raised with its model.
The live check still runs on `gpt-6-astra` when the account has it. The script header
and the README now say plainly that the copy freezes codex's model list, and that the
script should run again whenever OpenAI releases a model.

## Tests

- `tests/smoke.py` checks that every family name runs its newest model, and it
  submits all 32 names to confirm each `turn/start` carries exactly its model and
  effort. Every model and effort pair must read back as a name that runs the same
  pair: a family name wherever one exists, a pinned name for a model its family has
  left. A steer must go through under any name for the running model and be refused,
  sending nothing, under any other. Resume must report the model codex ran, not the
  name the caller passed.
- `tests/enable_1m_sim.py` adds the reported case. It starts from a catalog built on
  2026-09-06, with Astra and GPT-5.6 raised, and a live catalog that now has the three
  new models. They must show up in codex's own order, raised, with no warnings.
- Checked live against codex 0.159.0. Both editions of the script ran in isolated
  homes: the new models went from hidden to listed by the app-server's `model/list`,
  and each of them runs at 997,500. Re-runs and `--revert` behave as before. Through
  the bridge, `luna-medium` and `terra-medium` ran `gpt-6-luna`, `sol-high` ran
  `gpt-6-sol` and `astra-medium` ran `gpt-6-astra`. The pinned `gpt-5.6-sol-high`,
  `gpt-5.6-terra-medium` and `gpt-6.1-sol-high` ran exactly those models. All of them
  ran at 997,500 per codex's own session record. The resume, fork and lifecycle live
  tests pass.

## Upgrade

Install `claude-codex-bridge-v0.16.0.mcpb` and restart Claude Desktop. Then fetch the
script again and run it, so the new models reach codex's model list at 1,050,000:

```bash
curl -fsSLO https://github.com/Alexander-Stulov/claude-codex-bridge/releases/latest/download/enable-1m-context.sh
bash enable-1m-context.sh
```

```powershell
Invoke-WebRequest https://github.com/Alexander-Stulov/claude-codex-bridge/releases/latest/download/enable-1m-context.ps1 -OutFile enable-1m-context.ps1
powershell -ExecutionPolicy Bypass -File enable-1m-context.ps1
```

codex 0.159.0 or newer is recommended: its catalog carries GPT-6 Sol and Luna. macOS:
double-click the `.mcpb`. Windows: Claude Desktop → Settings → Extensions → Advanced
settings → Install Extension, from a local folder. Prerequisites and the full
documentation are in the [README](https://github.com/Alexander-Stulov/claude-codex-bridge#readme).
