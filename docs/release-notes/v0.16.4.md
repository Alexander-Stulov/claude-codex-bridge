The 1M-context scripts now raise the window to **950,000**, not 1,050,000, so long
threads compact instead of failing.

| | Was | Now |
|---|---|---|
| Catalog window | 1,050,000 | 950,000 |
| Effective window (95%) | 997,500 | 902,500 |
| Codex compacts at (90%) | 945,000 | 855,000 |

At 1,050,000, long threads in the Codex app and through the bridge stopped with
*"Codex ran out of room in the model's context window"*. Upstream rejected requests
once their input reached about 920,000 tokens, but codex compacts only at 90% of the
window, 945,000, so compaction never ran. At 950,000 it runs at 855,000, about 65,000
tokens below the point where requests were refused.

The `tokens_before_compaction` runway the bridge reports follows the new window.

## Verified

- Two failed `gpt-6-astra` threads: the last request that succeeded carried 920,192
  input tokens, and every request after it failed with `context_window_exceeded`.
  Neither thread had compacted.
- The 1M script, re-run with codex 0.166.0, raised 8 models. A `codex exec` on
  `gpt-6-astra` then reported `model_context_window` 902500.
- `tests/enable_1m_sim.py`, with both Bash and PowerShell editions.
- `tests/smoke.py`, including the compaction-runway figures for the new window.

## Upgrade

Re-run `scripts/enable-1m-context.sh` (macOS/Linux) or `scripts/enable-1m-context.ps1`
(Windows), then restart Claude Desktop and the Codex app. A catalog built by an earlier
script stays at 1,050,000 until you do. Install `claude-codex-bridge-v0.16.4.mcpb` for
the matching runway figures.
